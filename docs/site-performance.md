# 网站加载与并发访问优化

更新日期：2026-09-08。对象为 `https://tapeout.cc.cd/` 的玩家页面、公开读取服务和 Nginx。本文区分代码与配置改动、隔离模拟结果、生产测量和后续扩容计划；模拟并发数不代表已认证的线上承载人数。

本轮主要减少三类开销：首次打开时不需要的记录请求、多个访客重复触发的公共链上查询，以及静态资源的传输和代理成本。购买页现有提前准备继续保留，交易前的账户、网络、合约身份和购买内容校验不因展示层提速而删除。

## 前端减少重复工作

原页面打开任意页签时，都会查询当前场次中奖记录、三个场次的播报、销毁记录、奖金公示和退款公示；连接钱包后还会查询两个个人记录区域。当前场次的第一页中奖记录与播报存在重复，未显示的区域也每 10 秒查询一次。

现在只为当前页签读取相应记录。全站中奖播报保留；首页仍自动读取已连接账户的退款数据；个人参与页、领取奖金页和销毁页在进入时读取各自内容。相同完整 URL 的在途 GET 共享结果，结束后再次刷新会重新查询，不把已完成的账户数据长期缓存在浏览器中。

同一隔离浏览器脚本对改动前后版本的计数如下，首屏包含市场参考价请求。同期合并的个人中奖归属功能仍保留：已连接钱包的领取奖金页每轮需要 1 条个人归属查询及 3 条公共播报查询，共 4 条；不会将不同账户的结果与公共播报合并：

| 场景 | 改动前 | 改动后 | 单位与条件 |
| --- | ---: | ---: | --- |
| 未连接钱包，首页首屏 | 10 | 5 | HTTP API 请求数，模拟网络 |
| 已连接钱包，首页首屏 | 20 | 10 | HTTP API 请求数，包含模拟账户自动恢复 |
| 未连接钱包，首页一轮记录刷新 | 7 | 3 | HTTP 记录接口请求数 |
| 已连接钱包，首页一轮记录刷新 | 9 | 4 | HTTP 记录接口请求数，保留退款查询 |
| 非购买页，五次 2 秒调度 | 5 | 1 | 状态接口请求数；现在每 10 秒刷新 |
| 已连接钱包，非购买页同一调度段 | 2 | 0 | `eth_estimateGas` 方法调用数，不是 HTTP 请求数 |

购买页维持原来的状态刷新和准备节奏。其他页签及后台隐藏页面不进行购买预热；隐藏页面暂停自动记录、状态和销毁汇总查询，回到前台立即恢复读取。账户切换、语言切换、独立 `/burns.html`、首页退款和个人参与查询均包含在模拟验证中。

GET 遇到 HTTP 429 时按完整 URL 退避；只读 `/rpc` 批处理也尊重服务端 `Retry-After`。支持秒数或 HTTP 日期，缺少有效值时等待 5 秒，最长 60 秒。退避期间不持续向繁忙端点重试；后续正常刷新或用户操作到期后可再次读取。这不增加交易发送重试，已提交交易不会因为页面重试读取而自动重发。

实现入口：[`sparkdraw-player.js`](../bem-production-site/web/sparkdraw-player.js)、[`in-flight-reads.js`](../bem-production-site/web/in-flight-reads.js)、[`read-rpc-batcher.js`](../bem-production-site/web/read-rpc-batcher.js)。

## 公共状态查询合并

原公共缓存从发起读取时计算 3 秒有效期。上游变慢、读取超过 3 秒时，新访客可能启动第二组相同读取，进一步放大上游负载。

现在同一个缓存键的未完成读取始终共享同一任务，成功完成后才开始计算缓存有效期；失败会清理该项，下一次读取可以重新尝试。不同场次及不同数据类型的键独立，交易提交前的专用查询不使用这个公共展示缓存。

本地模拟中，200 个同场读取共享一组状态加载；其中后一批在超过旧 3 秒期限后到达，仍只产生该场景所需的 **14 次链上 RPC 方法调用**。这是验证查询合并的结果，未向生产环境发起 200 人或 200 连接的压力测试。RPC 方法调用、浏览器 HTTP 请求、连接数和在线访客数必须分别统计。

实现与回归：[`async-cache.mjs`](../bem-production-site/async-cache.mjs)、[`sparkdraw-service.mjs`](../bem-production-site/sparkdraw-service.mjs)、[`bem-service-cache.test.mjs`](../test/bem-service-cache.test.mjs)。

## 静态资源和连接处理

- 两张原 PNG 合计 **2,844,590 字节**。先生成原尺寸、解码像素一致的无损 WebP（合计 **2,117,852 字节**，减少约 **25.5%**），再提供匹配显示尺寸的响应式候选：横幅 384 / 640 像素宽，徽章 384 / 768 像素宽。浏览器按显示宽度和设备像素比选择 `srcset`，保留原尺寸 WebP 与 PNG 回退。较小候选经过等比缩放，不能称为与原图像素一致；实际下载量按最终浏览器测量计算。
- JS/CSS 预先生成 gzip 文件，由 Nginx 根据浏览器支持直接发送，减少传输量和重复压缩工作。`gzip_static` 的作用是选择预压缩的 `.gz` 文件，并不代表所有内容都无条件以 gzip 返回。[Nginx 官方说明](https://nginx.org/en/docs/http/ngx_http_gzip_static_module.html)
- 带内容哈希的静态资源从 `/var/www/bem2075-static/assets` 直接提供，减少静态流量经过 Node 服务的开销；动态 API 仍进入应用服务。
- 启用 HTTP/2，并配置到应用服务的上游空闲连接复用 `keepalive 32`，减少连接建立开销。这里的 32 是每个 worker 可缓存的上游空闲连接数，不是总上游连接上限，也不是可同时访问的用户数。[Nginx 上游 keepalive 说明](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#keepalive)
- `worker_connections` 从 768 调整到 4096。该值包括 worker 打开的各类连接，受文件描述符等限制；反向代理还会使用上游连接，不能把 4096 写成“支持 4096 人”。[Nginx worker_connections 说明](https://nginx.org/en/docs/ngx_core_module.html#worker_connections)
- 保留现有 API/RPC 限流规则，本轮没有通过放宽限流来宣称容量提升。

配置记录：[`bem2075-site.conf`](../ops/nginx/bem2075-site.conf)、[`bem2075-upstream.conf`](../ops/nginx/bem2075-upstream.conf)。

首屏速度还取决于服务器响应、关键资源何时被发现、下载时间及下载后的渲染时间；图片体积减少不能直接换算成所有手机的打开耗时。后续评价应记录真实关键内容的 LCP 及布局稳定性，而不仅是请求总量。[web.dev：优化 LCP](https://web.dev/articles/optimize-lcp)

## 生产测量与上线核验

服务器配置为 2 核、4 GB 内存。本轮检查的短时间样本约 99% CPU 空闲、约 3.1 GB 内存可用，只说明采样当时余量充足，不能推断活动高峰时的最大人数。

2026-09-08 08:19（北京时间）完成最终发布；服务器校验 58 个源文件/构建文件，公网核验 21 个首页、销毁页和静态资源，gzip 解压结果与原文件一致。HTTP/2、健康接口、旧哈希资源可用及私有路由保护均通过。本轮第一次部署加载公共缓存更新时重启了前台服务；最终响应式资源更新未重启服务，独立 keeper 全程未重启。同期上线的个人中奖归属及领奖权限功能已经合并保留，并加入浏览器回归。

两张实际 384w 图像传输约 61.7 KB 与 117.5 KB，桌面及手机截图目视清楚。确定的收益是静态下载量和重复请求减少；页面完成时间还受连接、代理、动态数据时序影响。首屏场次选择及中奖播报仍有异步布局变化，后续可以继续优化预留空间，不把单次 CLS=0 写成彻底修复。

本机证据目录为工作台 `网站修复记录/20260908-site-performance/`，保留 `before-page-load.json`、`after-page-load.json`（中间版本）、`final-page-load.json`、最终截图和 `最终加载对比.md`；`merged-final/deployment-result.json`、`live-verification.json`、各回归日志记录发布与核验。公开接口没有进行生产 p95 或人数压测，因此不提供未实测的最大在线人数。

最终合并版本通过 `pnpm test` **173 项**及钱包识别单测 **20 项**，合计 **193 项单测**；生产构建通过。另有 **28 个钱包购买模拟场景**与 **8 个请求负载浏览器场景**通过。浏览器回归覆盖慢响应在途合并、429 退避、隐藏页暂停、赢家才可领取、未中奖提示、账户切换即时撤销旧领取状态、断开钱包和语言切换。全部使用模拟账户与响应，没有真实钱包签名、授权、购买或生产压力流量。

## 访问量继续增长时如何处理

应先根据瓶颈扩容，不根据单个“在线人数”数字直接复制进程：

| 观测到的瓶颈 | 下一步 | 验证指标 |
| --- | --- | --- |
| 用户距离源站较远、图片/脚本下载慢或静态带宽高 | 为公共、带哈希的静态资源接入 CDN；HTML 使用明确更新策略，动态及账户相关 API 单独配置 | 不同地区的 LCP、静态缓存命中率、源站带宽和回源请求数 |
| RPC 超时、429、等待队列增大，尤其大份数估算较慢 | 配置有明确配额与监控的专用 RPC，按实际只读方法量、批量大小及 Gas 估算负载规划容量 | 上游 p95 延迟、429/超时率、排队长度、每秒 RPC 方法数 |
| Node CPU、事件循环延迟或公开记录读取成为瓶颈 | 拆分无状态前台读取服务与单写索引服务；先建立共享读取存储和一致的缓存失效，再部署多实例及负载均衡 | API p95/p99、错误率、CPU/内存、事件循环延迟和索引落后区块数 |
| 短时访问突增或大量客户端被限流 | 保留限流与退避，观察是否存在同一出口 IP 的正常用户聚集，再针对读接口容量调整策略 | 按路径的请求量、429 比例、来源分布和恢复时间 |

当前索引和服务状态存在 JSON 文件持久化及写入职责，**不能直接启动多个 Node 实例共用目录争写文件**。多实例前必须明确唯一写入者或迁移到支持并发与事务的共享存储；部署多台前台也不能重复启动链上自动执行服务。

完成静态和查询优化后，再在与生产隔离的环境进行分级负载测试：分别模拟未连接浏览、已连接只读查询、记录切换和交易预检，记录持续负载下的延迟、错误、RPC 配额及内存；真实交易量和链上确认能力另行评价。网站资源加载提速不等于钱包自身确认界面或链上出块速度同步提高。
